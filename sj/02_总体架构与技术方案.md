# 总体架构与技术方案

## 1. 推荐方案

推荐在当前桌面应用内部新增一个“局域网服务模块”，由 Rust 启动本地 HTTP 服务，对外仅在局域网网卡上监听。

整体架构：

- 桌面端主程序：Tauri
- 本地能力层：Rust
- 局域网服务：Rust HTTP Server
- 手机端页面：独立移动端 Web 面板
- 访问方式：手机浏览器访问电脑局域网地址

## 2. 为什么不用云服务

本功能目标就是纯本地、同 Wi-Fi、零服务器成本，因此不应引入：

- 云主机
- 远程数据库
- 第三方账号
- 外网 API 网关

否则会直接偏离需求。

## 3. 为什么推荐 Rust 内嵌 HTTP 服务

不推荐再起一个 Node 常驻服务进程。推荐直接在 Rust 中实现 HTTP 服务，原因如下：

- 现有本地文件能力已经在 Rust
- 路径安全逻辑放在 Rust 更统一
- 避免桌面端跨进程协调
- 打包后部署更简单
- 更容易保证所有危险操作都在同一层受控

## 4. HTTP 服务职责

Rust 侧新增局域网服务后，应承担以下职责：

- 提供移动端静态页面
- 提供手机端 API
- 维护当前工作目录状态
- 维护连接码和会话状态
- 维护已连接设备列表
- 统一做路径校验和文件访问

## 5. 手机端前端组织方式

推荐手机端前端作为独立的小型 React SPA。

不建议直接复用现有桌面端页面，原因如下：

- 桌面端状态模型太重
- 桌面端页面布局不适合手机
- 桌面端桥接依赖 Tauri `invoke`
- 手机端需要不同的页面密度和交互优先级

推荐做法：

- 在前端新增独立入口，例如 `src/mobile`
- 构建出一套静态资源
- 由 Rust HTTP 服务直接托管

## 6. 认证方案

第一版推荐：

- 桌面端点击开启服务时生成一次性连接码
- 手机端访问登录页输入连接码
- 认证成功后由后端设置 Cookie 会话
- 后续 API 依赖会话验证

会话建议：

- 有效期可设置为数小时
- 支持桌面端手动刷新连接码
- 刷新连接码时可选择同时使旧会话失效

## 7. 地址展示方案

桌面端需展示：

- 当前监听端口
- 本机可访问的局域网 IP 列表
- 对应的访问地址
- 当前在线设备列表

地址示例：

- `http://192.168.1.23:38421`
- `http://10.0.0.15:38421`

端口策略建议：

- 默认使用固定端口
- 若端口冲突，则自动回退到随机可用端口
- 最终生效端口必须反馈给桌面端设置页

## 8. 文件访问模型

手机端所有 API 都只能接受相对路径。

服务端内部流程：

1. 接收相对路径
2. 调用 `safeResolvePath(workspaceRoot, relativePath)`
3. 确认解析结果仍在工作目录内
4. 执行文件操作
5. 返回相对路径和元信息

禁止行为：

- 传入绝对路径
- 传入 `..`
- 传入带盘符路径
- 传入 UNC 路径
- 通过符号链接绕出工作目录

## 9. 预览策略

第一版预览优先追求稳定，不追求全能。

支持：

- 图片：直接返回可访问预览地址
- 文本：后端读取文本并返回内容
- PDF：优先使用浏览器原生能力

暂不强制支持：

- 视频在线播放
- 音频在线播放
- Office 文档预览
- 3D 文件预览

## 10. 上传下载策略

上传：

- `multipart/form-data`
- 单文件上传
- 限制 200MB
- 同名冲突直接拒绝，不覆盖

下载：

- 直接流式输出原文件
- 返回 `Content-Length`
- 便于手机端显示进度

## 11. 设备连接记录

第一版的设备记录只做“可见性”，不做复杂管理。

记录项建议包括：

- 设备标识
- 首次连接时间
- 最近活动时间
- IP 地址
- User-Agent 摘要
- 当前是否在线

## 12. 设计原则

整个模块实施时应始终遵守以下原则：

- 后端优先校验
- 相对路径优先
- 桌面端可控
- 手机端轻量
- 第一版克制
